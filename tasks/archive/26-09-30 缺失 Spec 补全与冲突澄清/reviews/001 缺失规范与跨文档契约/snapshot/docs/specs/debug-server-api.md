# Debug Server API

导航：[Spec 索引](index.md)；章节目录由[上下文工具](../harness/spec-context.md#受控阅读入口)从本文标题生成。

状态：现行约定与当前实现并列记录。本文规范 DEBUG 调试入口的安全边界和客户端契约；具体 RPC 方法、参数与返回值以运行时 `rpc.discover` 为准，不在 Spec 中复制一份容易漂移的方法全集。

## 适用范围与证据边界

适用于调试客户端、自动化脚本、DEBUG 构建接入、认证变更、RPC 新增或重命名，以及调试服务安全审查。Release 是否包含某项业务能力不由本文推断；本文也不承诺模拟器验证可以替代真机网络、前后台或配对验证。

静态核实来源：

- [DebugServer.swift](../../src/ios/Debug/DebugServer.swift)：监听、HTTP 路由、认证入口和服务重启。
- [DebugAuth.swift](../../src/ios/Debug/DebugAuth.swift)：配对、密文信封、时钟与重放防护、令牌存储。
- [DebugMethodRegistry.swift](../../src/ios/Debug/DebugMethodRegistry.swift)：运行时方法目录。
- [DebugJSONRPC.swift](../../src/ios/Debug/DebugJSONRPC.swift)：JSON-RPC 分发与错误。
- [MinisApp.swift](../../src/ios/MinisApp.swift)：DEBUG 启动和回到前台后的存活检查。

网络可达性、系统弹窗、USB 转发及真机前后台恢复仍需对应环境的运行验证。

## 服务生命周期与暴露边界

### 现行约定

- 服务只用于 DEBUG 构建，不得作为产品 API 或 Release 远程控制面。
- 默认端口为 `8321`。客户端不得假设所有构建、设备或网络都能访问该端口。
- 非本机访问必须经过配对和认证；关闭认证只允许作为明确、可见、可恢复的本地调试操作。
- 新增高风险 RPC 时，维护者必须同时审查发现信息、认证边界、数据最小化和副作用，不得只登记方法名。

### 当前实现

- `DebugServer` 使用 `INADDR_ANY`，日志报告 `0.0.0.0:8321`，因此代码层面会尝试监听所有 IPv4 接口，而不只是 `localhost`。
- App 在 DEBUG 启动路径启动服务，并在回到前台时调用 `restartIfDead(port: 8321)`。
- “绑定所有接口”是当前实现事实，不代表已经确认允许任意局域网暴露。实际防火墙、网络隔离和真机可达性为待验证项。

因此，客户端文档不得再写“只监听 localhost”。安全评审也不得把“认证默认开启”当成扩大监听面的充分理由。

## HTTP 入口

客户端应使用下列明确入口。现行安全要求是未知 HTTP 方法或路径返回明确错误，不得悄然执行相近操作；当前 POST 路径检查尚未满足这一要求，见下表后的实现偏差。

| 入口 | 用途 | 是否需要 RPC 密文信封 |
|---|---|---|
| `GET /schema` | 返回服务版本、认证状态和入口地址等机器可读信息 | 否 |
| `GET /`、`GET /skill` | 返回协议说明；根据 `Accept` 提供适合人或机器阅读的表示 | 否 |
| `GET /skill/examples/python` | Python 客户端示例；兼容 `/skill/examples/minis_rpc.py` | 否 |
| `GET /skill/examples/node` | Node 客户端示例；兼容 `/skill/examples/minis_rpc.mjs` | 否 |
| `GET /skill/examples/bash` | Bash 客户端示例；兼容 `/skill/examples/minis_rpc.sh` | 否 |
| `POST /pair` | 建立客户端令牌 | 使用配对协议，不是普通 JSON-RPC |
| `POST /rpc` | 执行 JSON-RPC 2.0 请求 | 认证开启时必须使用密文信封 |

认证被显式关闭时，当前实现仍接受 `/rpc` 的普通 JSON-RPC 请求；这属于兼容路径，不是新客户端的默认接入方式。

已核实的当前偏差：[DebugServer.swift](../../src/ios/Debug/DebugServer.swift) 只对 POST 的 `/pair` 做独立分支，其他 POST 路径会进入通用 RPC 处理，没有限定必须是 `/rpc`。例如发往未知路径的有效 RPC 仍可能执行。认证开启时仍检查信封，关闭时仍接受明文；此偏差不等于绕过认证，也不构成应依赖的路径别名。

后续收窄路径的验收：使用无业务副作用的有效认证 RPC 向未知路径发送 POST，应得到路径错误且不进入业务分发；明确的 `/pair` 和 `/rpc` 保持各自协议。当前仅核对分派源码，尚未执行这一运行场景。

## 配对、认证与消息保护

### 配对

- `/pair` 在设备批准后签发一个 32 字节客户端令牌。
- `plain: true` 仅允许回环/USB 转发来源，令牌会直接返回；局域网来源必须使用临时 X25519 公钥包装令牌。
- 模拟器当前会自动批准配对，以支持无界面自动化。这不证明真机批准弹窗、拒绝和超时行为正确。
- 配对令牌有客户端标识并持久化到 Application Support 下的调试认证存储。列举客户端的 RPC 不得返回令牌密钥。

### RPC 信封

认证开启时，`POST /rpc` 使用经过认证的加密信封，而不是裸 JSON-RPC：

- 请求与响应使用方向分离的派生密钥；
- 当前实现以 HMAC-SHA256 构造 CTR 密钥流，并采用先加密后校验 MAC；
- 每个请求使用随机 nonce；时间戳允许偏差为正负 120 秒；
- 服务维护最多 1024 个近期 nonce，拒绝重放；
- 客户端令牌空闲 30 天过期，刚批准的信任窗口为 10 分钟。

这些数值是当前协议 v1 的实现契约。修改任一项都必须同步协议版本、`/schema`/技能说明和客户端示例，并补充兼容或拒绝策略。

### 认证失败

缺少认证、密文校验失败、时间越界、nonce 重放、令牌未知或明文来源不允许时，服务必须拒绝请求，且不得先执行 RPC 再返回错误。日志可以记录诊断标识，但不得记录令牌密钥、明文凭证或完整敏感参数。

## JSON-RPC 与方法发现

`POST /rpc` 内层请求遵循 JSON-RPC 2.0：

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "rpc.discover",
  "params": {}
}
```

### 方法来源

- `rpc.discover` 是方法名、用途、参数和可用性的规范入口。
- [DebugMethodRegistry.swift](../../src/ios/Debug/DebugMethodRegistry.swift) 是发现目录的源码来源；[DebugJSONRPC.swift](../../src/ios/Debug/DebugJSONRPC.swift) 是实际分发来源。
- 新增、删除或重命名方法时，两处必须保持一致。未知方法应返回 JSON-RPC `Method not found`，并提示调用 `rpc.discover`。
- Spec 只维护能力族和约束，不手工复制数百个易漂移的方法参数。

当前能力族包括但不限于：视图与可访问性检查、交互和截图、日志与性能诊断、会话和聊天自动化、Provider/配置管理、备份诊断、浏览器和 MCP 调试。是否存在某个具体方法必须以目标构建的 `rpc.discover` 响应确认。

## 副作用与数据边界

- 只读检查与有副作用操作必须在发现描述中可区分。有副作用操作包括点击/输入、修改配置、发送聊天、创建或删除数据、触发备份恢复、切换认证等。
- DEBUG、需要配对并不等于操作天然安全。RPC 实现仍应执行自己的前提检查、参数校验和最小数据返回。
- 调试文件读取、数据库查询、日志导出不得用字符串前缀判断替代规范化后的目录包含关系。
- 认证开关、令牌撤销和客户端列举属于安全控制面；客户端不得缓存“曾经成功”并绕过下一次失败。

## 场景与验收

### 场景 A：新客户端安全接入

前提：DEBUG App 正在运行，认证保持默认开启。

1. 客户端读取 `/schema` 和 `/skill`。
2. 客户端调用 `/pair`；真机由用户批准，模拟器可自动批准。
3. 客户端使用获得的令牌封装 `rpc.discover` 请求。

可观察验收：未配对的裸 `/rpc` 被拒绝；配对后的密文请求返回 JSON-RPC 响应；发现结果至少包含 `rpc.discover` 本身，且不泄露令牌密钥。

### 场景 B：拒绝重放或过期请求

前提：已完成配对并保存一份有效密文请求。

可观察验收：完全相同的 nonce 再次提交会失败；时间戳超出允许偏差会失败；失败请求对应的业务方法没有发生副作用。

### 场景 C：服务前后台恢复

前提：DEBUG App 已启动服务。

可观察验收：App 回到前台后，存活服务继续响应；服务意外退出时 `restartIfDead` 能重新监听。真机验证必须记录设备、网络、前后台步骤和端口结果，不能仅引用源码调用。

### 场景 D：方法目录与分发同步

前提：新增或更改一个 RPC。

可观察验收：`rpc.discover` 的名称和参数与实际调用一致；未知名称得到 `Method not found`；相关 `/skill` 内容或客户端示例没有旧名字。

## 已知限制与待验证事项

- 已核实问题：历史 Spec 把服务写成仅 localhost、仅 POST，并手工维护大段方法表；三者都与当前实现不符，本文已移除。
- 已核实实现偏差：未知 POST 路径仍进入通用 RPC，详见[HTTP 入口](#http-入口)；严格路径要求尚未完全落实。
- 待验证：真机在 Wi-Fi、USB 转发、VPN 和前后台切换下的实际可达性及配对 UI。
- 待维护者确认：长期是否应继续绑定所有 IPv4 接口，还是默认收窄到回环/显式启用 LAN。确认前不得把当前 `INADDR_ANY` 写成产品承诺。
