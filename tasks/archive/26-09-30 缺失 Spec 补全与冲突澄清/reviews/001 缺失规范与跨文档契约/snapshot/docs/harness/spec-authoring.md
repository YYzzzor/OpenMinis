# Spec 写作与维护

状态：已确认的 Spec 治理方向，随 2026-09-29 实施接入。适用于新写、修改或验收长期 Spec；只查一个接口时从 [Spec 索引](../specs/index.md)进入，不必先读本指南。

## 职责与维护时点

Spec 同时面向维护者和 Agent：说明适用场景、预期行为、条件与例外，以及如何验证。任务记录保存本次目标、取舍、实施过程和证据，长期 Spec 保存以后仍适用的约定；不要把一次执行日志堆入规范。

规划时先读现行适用章节，将拟改变的行为与验收写入任务并确认。实现与验证后更新长期规范，保留验证边界；归档前记录改了哪些 Spec，或说明本任务为什么不需要改。新增文档、改标题或 description 后重新生成并检查索引。代码结果不符合要求时应修复或明确保留问题，不得把缺陷改写成预期行为以通过验收。

## 描述、标题与链接

每份 Spec 使用文件开头的单行 YAML `description`，简短说明覆盖范围及适用任务。正文首个一级标题给出文档名。示例：

```markdown
---
description: 日历重复创建的参数、结束条件、兼容接口与已知验证限制。
---

# 日历重复创建接口
```

description 是描述的唯一维护源；[生成索引](../specs/index.md)复用它，不在 AGENTS.md 或另一份清单手写相同描述。标题树由[上下文工具](spec-context.md#受控阅读入口)直接从正文生成，不维护第二份手写章节目录。

使用清楚的 ATX 标题（`#` 到 `######`），让每个小节覆盖一项可理解的主题。范围、定义和前提放在文档或父章节引言；相关旁支条件在正文用链接说明。引用其他 Spec 时说明关联用途，避免只有一串链接。无须额外维护每份文档的强制必读清单、依赖图或阅读账本。

文档没有硬性长度上限。长文档靠可定位标题和关联链接逐层阅读，主题确实独立时再拆分；不要机械按字数切文件。若完整小节反复无法放进输出预算，先记录实际场景，检查该节是否混杂多个主题，再决定调整粒度。不要省去例外或任意截断验收规则。

## 状态、场景与验收

区分三类内容，按文档或具体小节标明即可，不增加无用途的元数据：

- **现行约定**：已经确认、需要遵守的行为与限制。
- **现状说明**：带核查范围的实现描述，可能随代码变化；静态存在不等于设备操作成功。
- **草案或未来计划**：尚待确认或实现，不能因正文有 MUST、示例或 checklist 就当作当前能力。

用实际操作描述场景，以可观察结果表述验收。例如“创建每月第二个周二的事件后，查询未来三次发生日期”，比“支持复杂重复”更能说明验收。错误条件、授权前提、适用版本和已知限制在需要的地方写清楚；正文已有清晰示例和验收时可直接链接，不强制重复一套固定模板。

区分约定与验证结果。源码核对、单元测试、模拟器、真机测量分别证明各自范围；验证未完成的能力保持待验证，不能把旧分支证据当作新实现已验证。既有上游文档只做治理时，可补说明和验收入口，保留旧核查基线；不借机声称已经全量重验产品功能。

## 提交任务成果前

按改动风险选择验证：确认入口链接与标题定位有效，索引与源 description 一致，场景能找到相关条件和验收；文档修改运行 `git diff --check`。涉及上下文工具时验证完整章节、来源一致性和字符预算；纯文字变动不启动全产品构建。任务收尾按 [archive-task](../../.agents/skills/archive-task/SKILL.md)处理。

本指南不新增提交、推送、发布或外部写入授权。现有[协作边界](collaboration.md)继续适用。
