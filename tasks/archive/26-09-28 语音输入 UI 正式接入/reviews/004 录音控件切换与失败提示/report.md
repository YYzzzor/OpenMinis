## R1
- severity: minor
- requirement: scope.md item 2 (failure feedback): the voice-failure prompt must stop lingering over the recording controls; only the MinisToast duration was changed 2.2 -> 1.0, so the panel's failure text line becomes the durable channel and its lifetime/clearing behaviour matters.
- location: snapshot/src/ios/Views/Chat/Voice/InlineVoiceInputView.swift:29-36 (statusText; lastFailure early-return wins over all phase text) and snapshot/src/ios/Views/Chat/Voice/VoiceInputPanel.swift:227-232 (report sets lastFailure), 476-478 (startFromComposer), 703-704 (startVAD success), 1015-1020 (executeRetry), 1025-1030 (manualRetry), 1160-1165 (transcription success clears only transcribeError), reset()/clearAndRearm() (no lastFailure clearing).
- trigger: Within one composer session: first a failure that calls report (e.g. .noSpeechRecognized, .tooShort > 0.3 s, or a non-transient .transcribeFailed), then the user keeps talking in the same open capture session and the next segment transcribes successfully; or the user sends the message (clearAndRearm) / switches to the keyboard and back to voice (onDisappear -> reset(clearTranscript:false), onAppear -> prepare()).
- evidence: statusText returns viewModel.lastFailure.message before any phase-based text, and lastFailure is assigned nil only in four places (startFromComposer, startVAD success, executeRetry, manualRetry — grep shows lines 477, 704, 1018, 1028 and no other reset). A successful transcription sets transcribeError = nil (line 1165) but leaves lastFailure set; reset(clearTranscript: false) and clearAndRearm() never clear it. Consequently the single status row (VoiceComposerPanel.swift:135-148, identifier voice.status) can keep showing an expired error while recording continues (replacing '正在录音 · 可以停顿后继续说话') or while a fresh empty session is shown after a send / re-entry into voice mode, i.e. the 'failure prompt lingering over the recording controls' symptom the round targets is only removed from the transient capsule, not from the panel line. Inherited behaviour, not introduced by these two increments; the scope intentionally keeps the error line ('错误行保留'), so this is recorded as a residual risk rather than a regression of this round.
- verification: Static: re-read the five lastFailure assignment sites listed above and confirm none of them is reached on a later successful segment, on reset(), or on clearAndRearm(). Device/simulator: tap the mic, say something under the minimum so .noSpeechRecognized/.tooShort fires, then say a full sentence in the same session and check whether voice.status still shows the old error while the transcript grows; then use '键盘输入' and re-enter voice mode and check whether the old error is still shown instead of '点麦克风开始说话'; also send a message and check the fresh session's status row. If the intent really is 'keep the last reason until the next recording starts', document it next to statusText; otherwise clear lastFailure on a successful releaseTranscriptionResult and in reset().
- certainty: medium (state-machine paths and line numbers statically verified; the user-visible nuisance level is a UX judgement and was not observed on a device)

- severity: nit

- location: snapshot/src/ios/Views/Chat/Voice/VoiceComposerPanel.swift:154-161 (comment '只限制内容事务，外层输入容器仍保留模式切换时的伸缩动画' + .transaction(value: phase) attached after .padding to the whole VStack subtree, which contains sendControl() at line 142-143 and the transcript ScrollView/ScrollViewReader at lines 79-102) and the same pattern with the same class of claim in ComposerContentTransition at lines 24-33.
- trigger: Any transaction passing through the panel subtree that is unrelated to phase — e.g. an animation inside the caller-supplied sendControl() view, or the correction path's withAnimation(.easeInOut(duration: 0.2)) { viewModel.setTranscript(...) } at InlineVoiceInputView.swift:239 that reaches the panel's transcript Text.
- evidence: The mutation sets both transaction.animation = nil and transaction.disablesAnimations = true on every transaction that flows through the modified view; the inline comment asserts the narrower guarantee (only the phase-change transaction, later updates keep their animations). SwiftUI's transaction(value:_:) semantics — whether the value only gates re-application of the transform while the transform still applies to all transactions of the modified subtree — cannot be settled from this snapshot, and no reproduction was run, so the comment's guarantee is currently an unproven assumption. Impact if the transform is subtree-wide: animations inside the panel subtree are suppressed permanently, most visibly in the injected send control (whose content lives in the excluded AIChatView, so it could not be checked), and the two comments in this file would be inaccurate. No functionality (state updates, scroll target, hit testing) is affected either way, and the surface/stretch animation is outside the modified view, so this is cosmetic.
- verification: Device/simulator: enable Debug ▸ Slow Animations and toggle phase (tap mic, tap stop) while watching the injected send control and the transcript auto-scroll; or write a minimal SwiftUI reproduction (a subtree carrying .transaction(value: x){ animation = nil; disablesAnimations = true } plus one unrelated withAnimation update in that subtree) and observe whether the unrelated update still animates. If the scope is confirmed too broad, gate the flag on an actual change of the previous phase or correct the two comments; if it is confirmed value-scoped, capture that in a note/test so the invariant is not lost.
- certainty: low (depends on unresolved SwiftUI transaction(value:_:) scoping semantics; not reproduced in this read-only review)
