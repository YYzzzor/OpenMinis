- location: snapshot/src/ios/Views/Chat/AIChatView.swift:356-359 (reduceVoiceMotion / voiceTransition), 3377-3387 (returnToKeyboard), 3712-3713 (composer tap fallback); snapshot/src/ios/Views/Chat/Voice/VoiceComposerPanel.swift:24-32 (ComposerContentTransition); snapshot/src/ios/Views/Chat/Voice/InlineVoiceInputView.swift:106-115 (requestKeyboard/completeKeyboardRequest)
- trigger: Enable Settings > Accessibility > Motion > Reduce Motion, type a draft, tap the mic (voice.enter), then tap 键盘输入 (voice.keyboard); also reproduce the deferred branch by tapping 键盘输入 while a recording is being transcribed (requestKeyboard -> finishFromComposer -> completeKeyboardRequest runs later from onChange(of: isBusyForComposer)).
- evidence: returnToKeyboard is the only place that restores text focus on the return path, and it writes inputFocused = true exclusively inside the completion: closure of withAnimation(voiceTransition, completionCriteria: .removed) { voiceInputActive = false } completion: { DispatchQueue.main.async { ... inputFocused = true } }. voiceTransition is `reduceVoiceMotion ? nil : .smooth(...)`, so under Reduce Motion the transaction carries no animation at all, and the departing InlineVoiceInputView subtree has animations explicitly disabled by the ComposerContentTransition modifier applied at AIChatView.swift:3710, i.e. the .removed criteria is being asked to fire for a removal this code deliberately renders without animation. The completion's invocation for a nil-animation / animation-disabled removal is not documented, and no code sets inputFocused on this path outside that closure.
- verification: On a simulator/device with Reduce Motion ON: log inside the completion closure and around inputFocused (inputFocused is a plain @State at AIChatView.swift:234), then check whether the keyboard/cursor returns by itself after tapping 键盘输入, for both the idle transcript path and the finish-then-transcribe path; repeat with Reduce Motion OFF to compare with the behaviour the main agent reports verifying. Mitigation to note during triage: tapping anywhere in the composer still sets inputFocused (AIChatView.swift:3713), so the failure mode is a lost automatic hand-off, not an unrecoverable UI.
- certainty: medium - the call path is certain from source; whether SwiftUI invokes withAnimation's completion for a nil animation / animation-disabled removal was not verifiable at runtime in this review.

## R2
- severity: medium
- requirement: scope.md 用户需求 - 进入语音面板时保留背景平滑展开，且旧文字/按钮与新内容不得交叠；instant recording must be requested without waiting for the panel animation.
- location: snapshot/src/ios/Views/Chat/AIChatView.swift:3702-3710 (merged VStack + ComposerContentTransition), 3745 (ComposerSurface(voiceStyle: voiceInputActive)), 4692-4704 (ComposerSurface body using .glassEffect(...)/.background(shape.fill(...)) followed by .clipShape(shape)), 3373-3374 (withAnimation(voiceTransition) { voiceInputActive = true } immediately followed by voiceVM.startFromComposer()); snapshot/src/ios/Views/Chat/Voice/VoiceComposerPanel.swift:24-32, 155-157
- trigger: From text mode with a non-trivial draft (tall composer), tap the mic and watch the first ~0.32s (or use the preview 02 · 录音与检查对照 with 慢放切换动画 ON, where the surface animation is 3x longer while the content swap stays instant).
- evidence: The content subtree carries disablesAnimations = true for the mode-change transaction, so the freshly mounted voice panel takes its final (much taller) layout in the first frame, while the enclosing container/surface geometry is the only thing that animates - that is exactly the mechanism the scope reports as 'background keeps stretching'. ComposerSurface clips the content to that animating shape (.clipShape(shape) on both the glass and pre-26 paths), so the panel's lower rows (继续说话/发送/停止, status row, waveform controls) live inside a region of the shape that does not exist yet at t=0 and are revealed as the background grows; at the same time beginVoiceInput starts capture before/independently of the animation (startFromComposer is called synchronously, not from an animation completion), so a tap on 停止/发送 during that window targets a control whose visible/hittable area is clipped. The vendor verification summary only asserts 'no overlap' and 'background stretches', not that the clipped bottom controls are fully visible or tappable during the expand.
- verification: Capture the transition with slow motion/slow-motion preview frames at the moment of entering voice mode and check (a) whether the panel's bottom controls are partially clipped during the expand, and (b) whether they respond to a tap inside the 320ms window; if either is confirmed, the fix is to animate the panel's own height/background (or gate capture controls until the container has settled) instead of relying on the clipping surface.
- certainty: low-medium - mechanism is derivable from the source (instant child layout + animating clipped container + non-deferred capture start), but it depends on SwiftUI's layout-animation/transaction semantics and on whether clipShape constrains hit testing; the recording that could settle it was not available to me.
