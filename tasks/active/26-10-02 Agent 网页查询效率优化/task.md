# 26-10-02 Agent 网页查询效率优化

任务于2026-10-02确认，状态为 active。已在 `investigate/build8-agent-latency` 分支开始产品实现，首版代码及定向测试已完成，整体验收继续保持 active。

任务文档按照 [plan-task 的“写法”](<../../../.agents/skills/plan-task/SKILL.md#写法>)组织内容。

## 目标

Agent 要更快取得公开网页中的回答依据。

优化后，应用需要做到以下事项：

- 应用在正文可读时结束无用的加载等待。
- 应用让模型能够查找和继续读取长文。
- 应用保留准确的正文及来源信息。
- 应用保护浏览器的登录状态和用户操作。
- 应用在任务结束或停止后释放读取资源。

已有调查发现，正文可读时，浏览器仍可能等待其他资源加载。
长文截断也会增加重复定位和文件读取的次数。

### 名称与含义

| 名称 | 本任务中的含义 |
| --- | --- |
| `web_read` | 本轮新增的网页读取工具，主要取得公开正文。 |
| `browser_use` | 现有浏览器工具，负责搜索页面操作和交互。 |
| HTTP 读取 | 工具直接请求服务器返回的内容。 |
| WebKit | 应用使用的网页引擎，可执行页面脚本。 |
| 匿名读取 | 工具不继承应用浏览器已有的登录身份。 |
| 正文编号 | 工具返回的编号，代表一份已保存的固定正文。 |
| 当前用户请求 | 从用户发送消息到 Agent 完成此次回答的过程。 |
| 工具批次 | 模型在一次响应中提出的一组工具调用。 |
| 浏览器接管 | 用户手动操作浏览器，Agent 按原流程暂停。 |

### 第一版范围

| 输入或场景 | 第一版的处理方式 |
| --- | --- |
| 公开 HTML、纯文本或 Markdown | `web_read` 直接提取正文。 |
| PDF | `web_read` 返回资源地址和类型，说明内容尚未读取。 |
| 图片 | `web_read` 返回图片地址和类型，说明内容尚未读取。 |
| 网页要求登录 | `web_read` 报告认证限制。 |
| 服务器拒绝访问 | `web_read` 报告访问拒绝。 |
| 读取需要既有登录身份 | 模型在原许可范围内选择 `browser_use`。 |
| 读取依赖用户交互后的页面 | 模型选择对应标签中的 `browser_use`。 |

PDF 和图片可以交给现有文件工具、图像工具或用户处理。
应用需要验证后续处理是否成功。

维护者已明确本任务暂不实施 PDF 文字提取和 OCR。
PDF 保留类型识别、资源地址及未读取状态。

以下能力仍待决定，本任务不增加其实施范围：

| 待决定能力 | 需要确定的内容 |
| --- | --- |
| 图片识别 | 是否在 `web_read` 内读取图片内容。 |
| `web_read` 登录后读取 | 如何授权、保存身份和限制可见内容。 |
| 新的搜索服务 | 是否增加现有搜索入口之外的服务。 |

## 方案

### 1. web_read 先取得公开正文，再补充不足的内容

这个顺序用于减少整页加载的等待。
模型从现有搜索结果或用户网址中确定来源。

一次读取按以下步骤执行：

1. 应用在请求进入排队时记录总截止时间。
2. `web_read` 通过原生 HTTP 请求目标网页。
3. `web_read` 从响应中提取正文。
4. `web_read` 根据下表判断是否继续补充内容。
5. `web_read` 返回正文和读取说明。
6. 应用停止此次读取不再需要的加载工作。

| 读取情况 | 下一项动作 |
| --- | --- |
| 目标正文已经可读 | `web_read` 提取并返回当前正文。 |
| 页面只返回加载提示，或局部正文仍缺失 | `web_read` 检查页面明确提供的公开备用正文。 |
| 公开备用正文仍不足以取得目标内容 | `web_read` 使用独立匿名 WebKit 加载页面。 |
| 模型明确要求补充动态内容 | `web_read` 使用独立匿名 WebKit 加载页面。 |
| 总截止时间已到，或读取已经取消 | 应用结束调用，不再启动下一条读取路线。 |

“公开备用正文”包括网页明确提供的 Markdown 版本。
它也包括网页直接包含、且程序已有提取方法的正文数据。

HTTP、备用正文和 WebKit 加载共用一个总时间限制。
应用也限制请求次数，防止重复尝试形成循环。
这些阶段属于同一次 `web_read` 调用，不额外请求模型。

应用重新进入前台时，先检查已流逝的时间。
如果总截止时间已到，应用立即清理此次读取。

### 2. web_read 分项报告读取事实，模型判断证据是否充分

模型依据正文和用户问题，判断能否完成回答。
`web_read` 用小型 JSON 组织下列内容，正文保留 Markdown。

| 模型收到的信息 | 用途 |
| --- | --- |
| 正文 | 模型据此判断事实及其关系。 |
| 来源、标题和抓取时间 | 模型据此引用来源并判断时效。 |
| 读取状态和已知限制 | 模型区分部分正文、截断、访问限制及失败。 |
| 正文编号和已保存范围 | 模型定位或继续读取同一份内容。 |
| 相关未读取资源 | 模型获得资源地址，并判断还需要读取什么。 |

应用把详细阶段耗时、资源计数与内部请求时序保留在诊断中。
这些记录供执行者分析等待和资源释放，不逐项送入模型。
来源替换、超时和缺失范围仍在 JSON 中说明。
字段及示例见[结果契约](validation/result-contract.md)。

模型根据缺少的信息选择下一项动作：

| 信息缺口 | 模型请求的动作 |
| --- | --- |
| 已保存正文中有目标段落 | 模型提交正文编号和目标标题或关键词。 |
| 模型需要已保存正文的后续部分 | 模型提交正文编号和下一段的位置。 |
| 目标内容依赖尚未取得的动态页面 | 模型要求 `web_read` 使用 WebKit 补充内容。 |

HTTP 请求成功，只说明服务器返回了内容。
模型还需要判断正文能否支持用户要求的回答。
应用在最终模型输入处核对 JSON，避免二次截断破坏结构。

### 3. web_read 返回正文编号，让模型继续读取同一份内容

模型凭正文编号继续读取时，工具不重新下载网页。
一个编号始终对应一份固定正文。

长文处理按以下步骤执行：

1. `web_read` 提取正文并保留标题和段落。
2. `web_read` 保留代码标识符和表格结构。
3. `web_read` 记录正文与相关图片、链接的关系。
4. 应用暂存已提取的正文并生成正文编号。
5. `web_read` 返回正文编号和可继续读取的位置。
6. 模型提交正文编号及目标标题、关键词或位置。
7. `web_read` 从保存的正文中返回对应内容。

网页后来更新，不会改变已有正文编号对应的内容。
正文编号的有效范围如下：

| 使用条件 | 正文编号是否有效 |
| --- | --- |
| 原聊天、当前用户请求、原读取身份 | 有效。 |
| 其他聊天 | 无效。 |
| 后续用户请求 | 无效。 |
| 读取身份改变 | 无效。 |

应用限制暂存正文的数量和大小。
当前用户请求结束后，应用清理暂存正文。
应用只允许模型继续读取实际保存的范围。

应用还要检查工具结果进入模型前是否再次被截断。
目标片段必须出现在最终结果中，或能通过正文编号取得。

### 4. 模型按读取目的选择工具，已有充分证据就直接使用

| 用户需要什么 | 模型选择什么 |
| --- | --- |
| 读取已知公开网址 | 优先 `web_read`。 |
| 在公开长文中查找或继续读取 | `web_read`。 |
| 操作搜索页面 | `browser_use`。 |
| 点击、输入或滚动 | `browser_use`。 |
| 使用既有登录身份读取 | `browser_use`。 |
| 读取用户交互后的页面状态 | 对应标签中的 `browser_use`。 |
| 已有内容足以回答当前问题 | 模型直接使用已有证据。 |
| 内容缺失、需要更新或用户要求刷新 | 模型针对明确目标补充读取。 |

应用需要同步更新以下说明：

- 应用更新 `web_read` 和 `browser_use` 的工具说明。
- 应用更新 Agent 的系统提示。
- 应用更新 `minis-browser-use` 的命令行使用说明。

模型可以使用 `browser_use` 已合法返回的内容。
应用不能将登录凭据或私人正文复制到匿名读取存储。
`web_read` 和 `browser_use` 的结果都保留来源与身份范围。

### 5. 应用隔离页面状态，并共同限制渲染资源

`web_read` 使用独立的匿名 WebKit 对象。
它不导航或清理 `browser_use` 的现有标签。

应用要分别管理以下状态：

| 状态 | web_read 的处理方式 |
| --- | --- |
| 网站数据和登录凭据 | 应用使用独立匿名网站数据存储。 |
| 当前页面和导航 | `web_read` 只导航自己的 WebKit 对象。 |
| 浏览器输入和显示尺寸 | `web_read` 不修改现有标签的设置。 |
| 用户正在接管浏览器 | 应用保留原有接管等待和恢复流程。 |
| 读取完成或超时 | 应用不因此提前解除浏览器接管。 |

`web_read` 和 `browser_use` 都消耗同一设备的资源。
应用需要共同统计用于加载页面的 WebKit 对象。
每项占用都记录所属聊天和工具调用。

| 资源情况 | 应用的处理方式 |
| --- | --- |
| 运行中的 WebKit 对象数低于总上限 | 应用允许新的读取继续执行。 |
| 运行中的 WebKit 对象数已达总上限 | 应用有时限地排队，或报告资源限制。 |
| 浏览器标签正在使用或接管 | 读取请求不能抢占该标签。 |
| 出现资源压力 | 应用先清理可释放的读取缓存或临时 WebKit 对象。 |
| 读取因此不能继续 | `web_read` 报告受限或未完成。 |

应用限制运行中的 WebKit 对象数量和等待请求数量。
具体上限依据代表性的 iOS 测量确定。
WebKit 对象数量不能直接代替实际内存和能耗测量。

现有 `BrowserTabPoolRegistry` 的标签上限是8个。
它只统计已注册的浏览器池。
新的匿名 WebKit 对象需要纳入共同资源统计。

### 6. 应用按触发范围停止工作，迟到内容不能重新启动读取

| 触发 | 应用结束的范围 |
| --- | --- |
| 单次读取超时、异常或内部取消 | 只有该次读取。 |
| 用户点击工具气泡上的停止按钮 | 当前批次中的 `web_read` 和 `browser_use` 调用。 |
| 用户停止当前会话 | 当前会话活动任务中的 `web_read` 和 `browser_use` 调用。 |
| 用户删除会话 | 应用先停止该会话任务，再按原生命周期删除数据。 |

被结束的调用需要清理以下工作：

- 应用取消该调用的网络请求。
- 应用移除该调用等待执行的请求。
- 应用停止该调用的临时网页加载。
- 应用解除该调用的等待和观察任务。
- 应用清理该调用尚未提交的内容。

取消之后才返回的内容，仍对应原工具调用。
应用丢弃已取消调用的迟到内容，不再次启动读取。
应用也不能把迟到内容写入其他工具的结果。

其他聊天的任务不受扩大清理范围的影响。
停止任务保留已提交结果和既有登录。
网页已产生的外部副作用不会因停止而自动撤销。

| 时间与资源 | 超额排队、超时或触发停止。 | 应用按规定范围结束工作并释放资源。 | 检查实例、请求和队列的实际状态。 | R1–R6。 |
| 工具共存 | 已有证据足够，或结果乱序完成后重新加载。 | 模型不重复读取已有充分证据，结果对应原调用。 | 真实 Agent 轨迹及保存记录。 | W5–W6、A4。 |
| 完整查询 | 同模型多次查询，并比较前台和锁屏。 | 回答依据充分，测量能说明耗时与资源表现。 | 完整查询记录及真机测量。 | A1–A4。 |

已知的多图片协议问题仍作为独立依赖处理。
测试不能将协议错误算作网页读取已通过。

## 决定

### 当前不实施 PDF 提取和 OCR

本任务不实现 PDF 页内文字提取或扫描、图片 OCR。
测试保留 PDF 资源交接及未读取说明。
相关内容能力案例保留为后续资料，当前不要求执行。
官方设计依据及已确认的执行安排见[设计参考](research/04-web-read-design-references.md)。

### 已确认的结果格式与测试安排

- 模型收到小型 JSON，正文使用 Markdown 字符串。
- 应用保留来源、限制及实际可用的续读信息。
- 详细耗时、资源计数和请求时序保留在诊断中。
- 测试按20个主要组执行，关键变体逐项覆盖。
- 真实 Agent 使用5类代表查询，不将66场景全部重复为完整查询。
- 本版设计只采用官方资料，暂不考虑 Pi 社区扩展。

Harness 的任务正文及 L1 上下文组装上限已统一为25KB。

### 已确认的五项约束

- 读取工具可以补充尚未取得的正文。
- 应用隔离匿名读取身份。
- 应用落实总时间限制，并实际释放资源。
- 应用保留长文在最终模型输出中的可读范围。
- 测试通过真实 Agent 查询验证整体效果。

### 已确认的工具共存要求

- 模型优先用 `web_read` 读取公开正文。
- 模型用 `browser_use` 读取登录或交互相关内容。
- 模型直接使用已有的充分证据。
- 应用共同统计 `web_read` 和 `browser_use` 的资源。
- 应用明确调用、批次和会话的停止范围。
- 应用把结果对应到原工具调用。

### 锁屏对照使用相同的后台配置

维护者已开启以下应用设置：

- 维护者开启“增强后台运行”。
- 维护者开启“实时活动”。
- 维护者开启“任务通知”。

系统已允许 MinisX 通知和实时活动。
前台和锁屏对照将保持上述配置一致。
此前缓慢不能直接归因为这些权限未开启。
锁屏是否影响效率，仍由真机测量确认。

### 证据和能力范围保持原约定

| 情况 | 判定方式 |
| --- | --- |
| 原手机调查、模拟器或 Pi 实验 | 测试保留各自原有证据范围。 |
| 本地网站或 macOS 探针通过 | 测试不据此宣称新 iOS 工具已经提速。 |
| 第一版遇到 PDF 或图片 | 测试先验证限制识别和资源交接。 |
| `browser_use` 使用既有登录 | 工具遵守原有许可。 |
| 增加 `web_read` 登录能力 | 维护者另外确定能力范围。 |
| 高德价格查询依赖图片 | 测试需要实际读取图片内容。 |
| 高德查询遇到多图片协议问题 | 测试记录独立依赖及其处理结果。 |

具体资源和时间上限仍依据 iOS 测量确定。
新读取请求不能借用会抢占活动标签的资源分配路径。
单次读取取消不能借用会扩大停止范围的清理路径。
