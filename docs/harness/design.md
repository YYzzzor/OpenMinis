# OpenMinis 开发 Harness 设计

状态：设计基线已获用户认可；本文固化讨论结果，运行机制已开始实现，验证结果以实施任务为准。
日期：2026-09-11

## 目标和边界

为 OpenMinis 的开发提供跨会话恢复、任务意图对齐、独立代码审查，以及经过用户审核的规则改进。采用 Markdown、少量 Agent Skills 和脚本。小任务直接执行和验证；复杂或跨会话任务才持久化完整记录。

本 Harness 辅助开发 OpenMinis，不是应用内 Agent 的运行框架。第一版不引入 Trellis、Superpowers、任务数据库、自动发布或固定多 Agent 流水线。科学计算项目的案例只用于理解用户对流程的顾虑，不作为 OpenMinis 的领域要求。

## 文件与职责

- `AGENTS.md`：少量有效规则和恢复入口；新增内容见已批准提案。
- `docs/tasks/active/`：当前任务；简单记录为单文件，有审查附件时使用任务目录。
- `docs/tasks/archive/`：完成或取消的任务，需要时创建。
- `docs/specs/`：维护中的长期行为约定；已有实现说明不能自动提升为强制规范。
- `docs/harness/proposals/`：共用规则修改及审批状态。
- `.agents/skills/`：共享恢复、审查等技能，实施时按需创建。
- `scripts/harness/`：快照、调用和验证等确定性操作，实施时创建。

任务标题和文件名／目录名使用 `YY-mm-dd Name`，日期为创建日期；归档时保留原名。任务格式见 [record-formats.md](record-formats.md)。实施状态见 [实施任务](<../tasks/active/26-09-11 实现 OpenMinis 开发 Harness/task.md>)。

## Spec 上下文

采用索引常驻、正文按需读取、默认按完整小节读取。唯一简短索引位于 AGENTS.md；任务记录区分必读条款与参考材料，并随委派和审查传递。短文档或上下文不确定时读取全文，所选规则的定义、适用条件和例外不可省略。

审查保留完整原文快照与摘要，向 reviewer 提供必读小节和参考定位，必要时从同一版本继续读取。固定快照不等于全文自动注入；常驻索引也不意味着全量规范始终加载。自动提取无法判断语义依赖，需由发起者补足依赖章节。具体约定与入口见 [Spec 上下文](spec-context.md)。

## 角色和写入边界

主 Agent 保持对目标、验收、集成和最终结果的责任，默认完成小修改或需要连续共享上下文的工作。当子任务边界明确、可独立推进与验收，且预期收益超过交接成本时，使用 sub-agent；不要求每项任务都委派。委派输入包括目标、约束、验收、相关决定、允许修改范围、依赖以及预期返回内容。执行者发现需要扩大范围时先协调。

在已确认目标与授权范围内，自主完成必要工作，可逆的局部实现选择自行处理。缺失信息会实质改变目标、范围或验收，或需要新的授权时才询问。某步受阻时继续完成不依赖它的工作。已批准计划内的实施不重复请求规则审批；执行环境与外部调用的权限边界仍然有效。

教学规则只在用户请求代码讲解、分析或学习时展开；实现、审查和进度报告提供评估工作所需的说明。CodeGraph 不可用、索引过时或证据不足时直接阅读与搜索源码，同步警告不限制读取其他必要文件。

主 Agent 写任务记录与意见处理记录；执行者写指定范围代码；Pi 默认只读审查，由调用脚本保存原始输出。并行执行者避免同时修改相同文件。主 Agent 可以更换，任务责任通过文件交接，不依赖原子 Agent 存活。

## 恢复协议

1. 从用户消息定位任务；未指定时查看活跃任务，有多个合理候选才询问。
2. 阅读任务的目标、恢复信息、决定、未解决问题和相关有效规范。
3. 核对实际分支、HEAD、暂存/未暂存/未跟踪状态及必要的子模块状态。
4. 记录不一致时先核实，不根据旧文档覆盖代码、不自动切换或清理含改动的分支。
5. 简短报告恢复位置，继续可执行的下一步。

在完成可验证工作、重要决定改变、出现阻塞或交接时更新任务。关键状态采用临时文件写完后替换等方式，避免半写文件。异常中断恢复到最近可核实检查点；不承诺保存全部内部推理或恢复所有运行进程。

待审核提案不属于生效规则，恢复时必须保留其审批状态。已被用户否定的方向及原因应留在相关任务中。

## 审查协议

### 输入绑定

主 Agent 完成检查和适当测试后，准备固定的审查材料：

- 基准提交、HEAD、分支名、Git 状态及 merge/rebase/冲突情况。
- 实际审查的完整代码快照及摘要标识；暂存和未暂存补丁、新增文件需足以还原实际内容。
- 任务目标、验收条件、相关规范的版本或内容快照。
- 变更范围、必要关联代码、已执行验证及未验证部分。
- 涉及子模块时记录其版本与改动；明确忽略文件、生成物和依赖的排除范围。

仅分支名、HEAD 或 `git status` 都不足以标识未提交的实际代码。第一版优先使用隔离且固定的快照，不让 reviewer 在持续变化的工作区上得出版本确定的结论。具体快照格式、完整性校验和存储策略在脚本设计时验证。

### 执行与结果

Pi + DeepSeek 直接读取目标和代码，独立判断行为偏差、遗漏和风险；主 Agent 总结仅作辅助材料。Pi 非交互调用优先，RPC 按需要引入。模型名称作为工具配置，不硬编码进通用 skill。

每轮请求、原始报告和处理记录分别保存。原始报告不被处理结果覆盖。结果包含问题标识、对应要求、代码位置、触发条件、依据、严重程度和建议验证方式；区分确定缺陷与待核实疑点。

主 Agent 核实意见，记录接受、修复、不采纳或待用户判断及理由。修复后重新检查，行为变化触发针对性复审。旧报告不能自动覆盖新代码或新需求。未发现问题不等于全部行为已经验证。

Pi 的结论是待核实的审查输入，不直接决定验收。主 Agent 对照已确认意图、代码和相关验证判断问题是否成立、严重程度是否合理、建议是否必要，并依据验收条件作出判断。Pi 标记 blocking 不自动否决验收，no_findings 也不自动通过；不采纳意见必须保留具体依据，不能只用实现者的自信反驳。影响验收的实质疑点未解决时保持未完成；涉及目标或范围取舍时交给用户。该原则经用户明确批准，见 [提案 004](proposals/004-review-judgment.md)。

审查覆盖提案：行为变更、缺陷修复和跨模块重构默认经过主 Agent 检查与 Pi 审查；纯注释、排版和简单文档修改由主 Agent 检查，按需独立审查。此项已在提案 001 中获用户批准。

### 失败与分歧

启动前保存请求和快照标识；调用完成后保存进程状态与输出。超时、连接失败、空输出或报告不完整均为审查未完成。脚本只能验证结构与绑定，不能证明审查推理正确。只对可恢复的调用失败做有界重试；具体次数和时间预算由适配配置决定。

验收未满足或必要验证未完成时不能标记完成。运行环境缺失应明确记录，例如 Linux 不能替代 Xcode/真机验证。争议涉及用户目标时交给用户判断。重复无效修复应转入诊断并记录证据，而非无限审查循环。

## 纠偏与受控改进

显著偏差包括做错目标、违反明确约束、重走已否定方向、未经验证就宣布完成。

发现后自动纠正当前任务并记录事实。先判断问题属于局部实现、缺失上下文、过时规范、skill 指令还是共用流程。局部问题优先局部解决，不将每次错误变成全局规则。

影响后续任务的修改必须先提出：偏差事实、原因（区分证据和假设）、具体变更、影响范围、验证与撤销条件。用户审核后才能实施。批准只适用于明确版本的提案；变更范围显著扩大时重新审核。无人回应、模型赞同或测试通过均不代表用户批准。

已经批准的计划内实施不再重复请求规则审批。此次对模糊指令的收窄及其批准依据见 [提案 002](proposals/002-instruction-scope.md)。

提案状态区分 proposed、approved、rejected、implemented、verified、reverted。批准记录包含用户确认的内容及时间。验证失败可以提出进一步调整或撤销计划；删除、合并和缩小规则也是改进。

## 工具适配与迁移

共享 skill 使用标准 `SKILL.md` 和相对引用，描述结果与约束；不依赖 Codex 专有工具名称、会话编号、UI 元数据或 Pi 扩展钩子。工具调用和权限在各自适配入口处理。工具白名单不被描述为操作系统沙箱。

OpenMinis 配置包括 `src/ios` 范围、个人分析与注释使用的 `ios-annotated` 分支、只读 upstream、验证入口和文档位置。其他开发使用任务确定的分支，未确定时沿用合适的当前开发分支，不将个人改动放入 main，不自动迁移或清理已有改动。通用机制不硬编码这些值。跨工具恢复使用任务文件与代码状态，不转换原生会话历史。

本机工具与真实调用的已验证情况见 [验证记录](validation.md)，避免在设计中维护另一份易过时的环境状态。不读取或写入报告中的凭据，不为迁移提前建设安装平台。

## 验证和试用

实现前固定案例，实现后在临时工作区验证：正常恢复、过时记录、突然中断、dirty 工作区快照、审查版本变化、Pi 超时/错误/残缺输出、待审核规则不生效、小任务不过度触发。测试应检查行为和产物，不只匹配文档标题。

根据目标与相关风险选择足够的检查。检查通过且没有新改动、失败或未解决疑点时，不重复或扩大测试。无法执行的检查明确记录，不以无关测试替代；主 Agent 检查与 Pi 独立审查仍按已确认职责分别进行。

分别验证 Codex 和 Pi 的实际执行；格式可读不代表行为兼容。随后选择两三个真实 OpenMinis 任务，记录恢复成本、审查遗漏与误报、耗时/token（可获取时）和维护负担。初步通过只代表机制可用，跨模型审查收益仍需实测。
