# MinisX 项目技能使用说明

这份文档说明本项目共同维护的技能：什么时候用、会得到什么结果，以及哪些决定需要你参与。你可以直接用自然语言提出任务，无需记住调用命令。

## 先看这张表

| 技能 | 什么时候用 | 你会得到什么 |
| --- | --- | --- |
| [plan-task：规划任务](../../.agents/skills/plan-task/SKILL.md) | 开始新功能，或目标、约束、技术路线还没有说清楚 | 一份你能理解并确认的开发计划 |
| [ios-ui-design：原生界面设计](../../.agents/skills/ios-ui-design/SKILL.md) | 设计或改进原生 iOS 界面，希望层级清楚、反馈及时、交互符合苹果平台习惯 | 有依据的设计建议、重要取舍和可观察的验收方法 |
| [resume-task：恢复任务](../../.agents/skills/resume-task/SKILL.md) | 换会话、换 Agent，或中断后继续已有任务 | 对照实际代码核实的进度，以及可以继续执行的下一步 |
| [review-task：审查任务](../../.agents/skills/review-task/SKILL.md) | 行为改动、缺陷修复、跨模块重构需要检查，或你明确要求审查 | 针对固定版本的问题报告、逐项处理结果和验收判断 |
| [archive-task：任务归档](../../.agents/skills/archive-task/SKILL.md) | 记录任务收尾，或恢复时发现可能已经完成 | 有证据的归档判断，以及归档位置或未完成原因 |

五个技能分别提供任务规划、原生界面设计、任务恢复、审查和归档支持。ios-ui-design 补充设计判断；具体写代码和运行测试由 Agent 按已确认计划及 Harness 执行。

## 1. plan-task：先把要做的事说清楚

### 你可以这样说

> 我想让 Agent 创建周期性日历事件。先确认目标和约束，解释可行路线及优缺点，给我一个计划，确认后再开发。

### Agent 应该怎么做

1. 看相关源码，确认现在已经能做什么、缺什么。
2. 询问会影响功能的关键问题。例如重复频率、结束条件，以及是否需要修改某一次事件。
3. 调查会影响选择的技术事实，解释可行方案和代价，并给出推荐。
4. 对适用的功能任务，用两张图解释功能位置与典型场景，再整理实现步骤和验收方法，与你确认后正式实现。

你主要判断想要的效果和能接受的取舍。Agent 负责说明 iOS 限制、现有代码和技术方案，不能只把陌生的 API 或框架名称列出来让你选。

### 确认稿包含什么

| 内容 | 要回答的问题 |
| --- | --- |
| 目标与范围 | 做完后我能做什么？这次明确不做什么？ |
| 方案与取舍 | 为什么选这条路线？其他可行路线有什么得失？ |
| 限制与假设 | 哪些已经查实？哪些还需要实际测试？ |
| 实现步骤 | 分几步做？每一步怎样检查结果？ |
| 验收标准 | 出现什么结果才算完成？哪些检查暂时做不了？ |

简单任务可以只有几句话。方案比较只在存在实际取舍时进行，不为每个任务凑出多条路线。已明确的目标和已批准的计划不重复确认。

### 规划时你会看到的两张图

涉及功能开发、模块协作或数据与状态变化时，Agent 会在前期规划中提供：

| 图 | 帮助你判断什么 |
| --- | --- |
| 功能位置与关系图 | 功能接在软件哪里、各部分负责什么、依赖谁；哪些已经存在，哪些计划新增或修改 |
| 典型场景运行图 | 从一个实际操作开始，处理顺序、数据与状态变化，以及关键分支是否符合你的预期 |

只画本次功能和直接相关部分，不绘制整个软件的完整运行流程。你主要判断职责和使用行为是否合理，不需要先掌握 Swift 或熟悉所有文件。单纯改文案、颜色或间距的小任务不强制画图。

规划图会标明它是拟议方案；实施发生相关变化时同步更新，交付前再对应到实际代码，并附关键文件或函数入口，方便你按图阅读和写自己的理解。图优先使用 Mermaid 文本，随现有任务记录保存；较长时拆成同目录文档并链接，不另建绘图任务。具体要求见 [规划技能](../../.agents/skills/plan-task/SKILL.md#用两张图解释设计) 和 [任务设计图记录](record-formats.md#任务设计图)。

### 确认如何生效

复杂开发和验证开始前，你会先看到真实使用目标、范围、验收证据、工作位置、设备/数据影响及停止条件。Agent记录你确认的版本和原话；任务文件、检查点或Pi报告不能代替你的确认。仅允许一次审查或工具操作，不会扩大成整个任务的授权。具体而明确的直接修改指令可以直接执行；已确认且范围不变的任务无需反复批准。

默认继续当前对话。只有你明确要求才新开工作对话；计划使用worktree时，Agent必须事先在对话中告知你，说明为什么需要、相比当前工作目录的具体收益，以及位置、分支和基线，经确认后再创建或开始使用；不能仅写入任务文件或事后通知。验证先跑通代表场景及可靠观察方式，再扩展；反复没有新增证据时应停下说明，而不是不断增加工具和测试轮次。

### 确认之后

按计划完成一条可测试的功能路径。项目的固定分工见 [AGENTS.md](../../AGENTS.md#codex-model-delegation)：主模型默认 GPT-6-Astra 负责需求、规划、协调、只读审核和最终验收；所有代码相关编辑，包括集成、小修改、测试及验证脚本、按审查意见修复，都委派给明确指定 `gpt-6-luna` 与 `xhigh` 推理强度的 GPT-6-Luna，由它运行相关验证并提交绑定最终版本和设备的原始证据。Luna xhigh 不可用时，主模型说明限制并继续独立规划或审核，不自动换模型或亲自改代码；偏离分工须用户明确授权。如果新证据要求改变已经确认的功能、重要技术路线或验收标准，Agent 应说明影响并与你重新确认相关部分。

第一版把目标澄清、按需调研、方案比较和计划定稿合在一个技能内，不设置独立原型阶段。后续有实际复用需求时再拆分。它参考 Matt Pocock 的 [目标澄清](https://github.com/mattpocock/skills/blob/main/skills/productivity/grilling/SKILL.md)、[多方案比较](https://github.com/mattpocock/skills/blob/main/skills/engineering/codebase-design/DESIGN-IT-TWICE.md)和[需求定稿](https://github.com/mattpocock/skills/blob/main/skills/engineering/to-spec/SKILL.md)思路，内容按本项目重新编写。

## 2. resume-task：换会话后继续，不靠猜测恢复

### 你可以这样说

> 继续“周期性日历事件”任务。先核对任务记录和当前代码，再接着做。

Agent 默认只在 tasks/active/ 发现任务，选定后读取已有目标、决定、验证结果、下一步和待确认事项，再核实当前分支、提交位置及未提交改动。已完成或取消的记录在 tasks/archive/，不会作为每次调用的默认背景读取；只有你指定历史任务或当前工作确实需要某份历史证据时才按需查看。

任务记录可能落后于实际代码。遇到差异时，Agent 应查明原因，不能为了让记录一致而覆盖你的修改。检查点是核对变化的摘要，不是完整备份，也不能恢复当时运行的进程。

你通常只需要说明要继续哪个任务。已有批准仍然有效；只有新的实质分歧或缺失信息才需要再次讨论。

## 3. review-task：检查实现是否符合已经确认的目标

### 你可以这样说

> 请对照已确认的计划检查实现，核实测试结果，再按 Harness 完成独立审查。

审查分三个部分：

1. **准备**：主 Agent 检查实现和可用测试，固定本轮代码与需求版本。
2. **独立审查**：启动全新的 GPT-6.1-Sol high 审查会话，使用 task_name 前缀 review_ 和 fork_turns=none；只读固定材料，聚焦真实缺陷及不必要的过度工程化/防御设计。
3. **处理与验收**：主 Agent 核实每条意见，记录修复或不采纳的理由，并判断是否达到验收条件。

产品缺陷应说明真实操作和可见影响，测试工具缺陷与证据不足单独列出；不能把工具修复建议当作你会遇到的产品问题。

审查目录会按本轮具体讨论内容命名，例如 `reviews/003 连续对话保留上次有效占比/`。前面的序号方便排序，后面的标题说明这一轮在查什么，不会只留下 `001`、`002`。同主题重试或复审也会在标题中说明，便于你直接浏览；命名规则见 [每轮审查记录](record-formats.md#每轮审查)。

审查意见需要核实；没有发现问题也不等于所有功能都已测试。原始报告会保留，处理结论另行记录。

你主要参与涉及需求取舍的决定。例如测试发现某个要求无法按原方案满足，是否接受调整应由你判断。

## 4. ios-ui-design：让原生界面清楚、连贯、好操作

### 你可以这样说

> 聊天输入区有些杂乱。请按苹果原生界面的设计原则，先检查信息层级和操作反馈，解释建议和取舍，确认后再改。

> 已批准的发送按钮反馈方案继续实施，范围不变。请结合 ios-ui-design 检查效果。

### 它会关注什么

- 哪些内容和操作最重要，导航、分组与布局是否容易理解。
- 按下、加载、成功、失败、取消时，用户能否知道发生了什么。
- 动画是否帮助理解，手势是否连贯，快速连续操作是否要等待。
- 文字、颜色和材质是否清楚；大字体、深浅色和辅助功能下是否仍然可用。

依据主要来自 Apple 的 WWDC 和人机界面指南；借鉴 Emil Kowalski 把设计原则整理成判断问题的方法。来源及项目应用见[Apple 依据与项目应用](../../.agents/skills/ios-ui-design/references/apple-design.md)。原生感包括熟悉的行为、清楚的层级与及时反馈，不要求到处使用玻璃或添加动画。

### 优先用 Canvas 一起调整 UI

后续 UI 调整优先使用 Xcode Canvas：Agent 提供与正式界面共用组件的预览，把尺寸、字号和间距等可调参数集中放置，写清中文注释、单位及联动关系，并告诉你在哪里修改和如何刷新。按实际需要展示几种状态作对照，例如一位、两位、三位数字。

你可以直接微调参数、观察效果；确认后，Agent 保留你的修改，核对正式界面使用同一套参数，更新注释及确认记录，并完成必要验证。键盘、手势、后台等 Canvas 无法充分验证的部分，再按任务范围使用模拟器或真机检查。Canvas 不适用或环境故障时，会说明限制并选择合适的替代方式，不强制每次 UI 小改动都增加独立原型阶段。

具体执行规范见 [Canvas 协作流程](../../.agents/skills/ios-ui-design/SKILL.md#优先用-canvas-协作调整-ui)。本偏好由维护者于 2026-09-27 确认并要求写入项目文档。

### 你需要参与什么

Agent 应先解释“要解决什么问题、建议怎样表现、为什么、有什么代价、怎样验证”，给出推荐，而不是让你选择陌生的动画参数。有实质差别的方案才比较；若你需要直观判断，可以在授权范围内制作少量可交互方案，不把原型作为固定阶段。

重要目标与取舍通过 plan-task 确认；已经批准的方案直接沿用。只要求检查时不会自行改界面。SwiftUI／UIKit 编码、构建、调试继续由已有工程能力承担，审查按 Harness 执行。

源码检查能发现部分问题，截图能检查静态外观；动画与手势还要看实际连续操作，触感等要按需上真机。Agent 会分别说明已验证内容和待验证内容，不能只凭“编译通过”就说界面体验已经达标。

## 实际使用时怎么衔接

| 你的情况 | 通常如何处理 |
| --- | --- |
| “为什么这个文件是 Objective-C？” | 直接解释，不启动规划或审查流程 |
| 有一个新功能想法 | plan-task；涉及原生 UI 设计取舍时结合 ios-ui-design，确认后实施、测试，再按 Harness 审查和验收 |
| 想让某个原生页面更清楚、更有苹果原生感 | ios-ui-design，在该页面范围内检查与建议；重要取舍接入 plan-task |
| 计划已批准，要求继续实现 | 沿用计划继续；跨会话时先用 resume-task 核实状态 |
| 测试不通过 | 在已确认范围内修复；重要路线或验收需改变时再讨论 |
| 只改一处已明确的文案 | 按具体指令处理并检查，无需完整规划或强制建任务记录 |

小任务的确认可以留在对话中；复杂或跨会话任务保存在 `tasks/active/`，命名采用 `YY-mm-dd 名称`。验收完成或取消后连同附件移到 `tasks/archive/`，不会自动进入后续任务上下文。详细约定见[任务记录格式](record-formats.md)，工具操作见[Harness 操作说明](operations.md)。

本说明覆盖仓库 `.agents/skills/` 中的五个共享技能。本机或插件提供的 SwiftUI、构建、注释等技能属于环境能力，按具体任务选用，不保证其他机器也已安装。本项目自己的规划和验收流程以 [AGENTS.md](../../AGENTS.md) 为入口。

如果当前工具没有自动发现项目技能，可以直接要求 Agent 读取表格中链接的 `SKILL.md` 再执行。技能是否实际被加载、任务是否完成，都要以本轮行为和验证结果为准。

## archive-task：判断并归档

任务收尾时主动使用，或在恢复时检查选定任务是否已完成。符合验收或明确取消后直接移动记录及附件，未完成则保留 active 并写明下一步；无需你另行提醒。详细判断只在 [archive-task](../../.agents/skills/archive-task/SKILL.md) 中维护。它是按需执行的技能，不是后台扫描，也未添加归档 Hook。
