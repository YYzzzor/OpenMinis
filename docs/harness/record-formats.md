# 记录格式草案

状态：提案 001 已批准，作为记录约定使用；示例不是当前任务的事实。可省略不适用字段，避免创建空附件。

## 任务命名

任务标题和文件名／目录名使用 `YY-mm-dd Name`：两位年、两位月、两位日，后接一个空格与简明任务名称。日期取任务创建日期，后续更新或归档不改日期。此约定经用户明确指定，见 [提案 005](proposals/005-task-naming.md)。

- 单文件：`docs/tasks/active/26-09-11 修复会话恢复.md`。
- 有附件的任务：`docs/tasks/active/26-09-11 实现 OpenMinis 开发 Harness/task.md`；内部 `task.md` 与附件名不重复日期。
- 归档保留同一名称，位置改为 `docs/tasks/archive/`。该目录按已有设计在需要时创建。

命令中的含空格路径使用引号；Markdown 链接目标使用 `<...>` 包围。已固定的历史审查材料不因当前任务更名而改写。

## 任务记录

```markdown
# <YY-mm-dd Name>
状态：planned / active / blocked / done / cancelled
更新：<时间>

## 恢复信息
分支：<实际分支>

工作区：<暂存、未暂存、未跟踪及未完成 Git 操作>
下一步：<具体行动>
待审批：<提案链接及状态，没有则写无>

## 目标与验收
<用户确认的目标和范围>
- [ ] <可观察的验收条件>

## 上下文与决定
<代码与文档入口及用途、已确认决定、否定方向及理由>
<待验证假设明确标记>

## Spec 阅读清单
必读：<文档路径 :: 完整标题路径（或全文）；用途与必要的依赖小节>
按需参考：<文档路径 :: 完整标题路径；用途>
<不适用时省略；审查阶段绑定原文版本，委派时传递同一份清单>

## 实现计划
- [ ] <可独立检查的一项工作>

## 进展与验证
<实现情况，与验收是否通过分别记录>

<请求、原始报告及处理记录的链接>
```

## 每轮审查

有审查附件时，将任务升级为目录；每轮使用独立编号：`reviews/001-request.md`、`001-review.md`、`001-resolution.md`。请求引用快照清单，快照清单应包含代码和需求文件标识、Git 状态及排除范围；具体机器格式待脚本实现确定。

原始报告包含：请求编号、快照标识、审查工具/模型/版本、实际覆盖范围、总体结论、问题清单。总体结论区分阻断问题、非阻断问题、未发现问题和无法完成审查。

Spec 原文完整保留在快照中，必读小节与参考定位分别进入请求。报告的实际覆盖范围列出阅读的小节及补充内容；快照清单绑定原文摘要和选择范围。选择方式见 [Spec 上下文](spec-context.md)。

每个问题使用稳定标识 R1、R2 等，记录严重程度、对应要求、代码位置、触发条件、证据、是否待核实和建议验证。不要仅给数值评分或通过结论。

处理记录逐条记录状态（已修复/不采纳/待核实/待用户判断）、理由、改动版本及验证证据。后续复审链接到原问题，不覆盖原报告。

处理记录分别列明 Pi 的建议结论与主 Agent 的验收判断，后者依据已确认验收条件、核实结果和未解决事项；有分歧时记录具体证据与理由。Pi 的 blocking/no_findings 标签不能直接作为验收结果。
