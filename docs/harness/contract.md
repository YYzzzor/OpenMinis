# MinisX Harness 契约

状态：已确认（2026-09-30）。此后 Harness 的其他文件以本文为准，不重复本文内容。

## 目的

让模型在**尽量少的上下文**下拿到**恰好够用**的信息，完成开发任务；让维护者随时知道任务进展，以及框架此时加载了什么。

## 五项职责

### 1. 任务

- **何时建记录：** 需要跨会话，或需要你确认验收的任务。一次会话能完成的小任务不建。
- **位置与命名：** `tasks/active/YY-mm-dd 名称/task.md`；完成或取消后整个目录移到 `tasks/archive/`。
- **内容（≤ 3KB）：** 状态、相关 Spec、目标、验收清单、决定（含否定方向与原因）、下一步；复杂任务可加实现计划。
- **验收清单：** 写“做成什么样”。有证据才打勾，并注明证据位置；用 Spec 规则编号引用，例如“满足 D2”。
- **实现计划（可选）：** 写“怎么做”，分步列出，完成一步勾一步；不与验收清单重复。
- **下一步：** 不设条数，写到下个会话读完就能直接开工；在会话结束且任务未完成时更新。会话内的临时步骤用工具自带的待办功能，不写入文件。
- **不写入：** 过程日志、原始输出、授权原话、Git 状态快照。
- **归档条件：** 验收全部打勾，或未完成项写明原因并经你同意；本任务新增或修改的 `[拟议]` 规则已全部处理（生效或按取消规则恢复）。

### 2. Spec

- **定位：** 长期有效的行为约定，只写“应该怎样”。“目前做到哪、验证过什么”属于任务。
- **写法：** 规则编号、正面表述、可测试；包含“不在范围内”、验收场景和代码入口。两种标记：`[待决定]` 表示还没有结论的问题；`[拟议]` 表示已确定、但尚未实现并验证的规则。范例：[用量、费用与余额](../specs/ios-usage-cost-and-balance.md)。
- **大小：** 单份建议 ≤ 7,000 字符；超出时按主题拆分。
- **读取：** 从 [Spec 索引](../specs/index.md) 选出相关文档，整份阅读。
- **更新时机：先写 Spec，后写代码。**
  - 规划时：把新增或修改的规则直接写进 Spec，标 `[拟议]`，任务的验收清单引用这些编号。新增规则分配新编号；修改已生效规则保留原编号，并附原文 `（原：……）` 作为恢复依据。任务记录分别列出新增和修改的编号。
  - 实现中：发现规则需要调整就直接改拟议规则；涉及需求变化的，先经你确认。
  - 验证通过：去掉 `[拟议]` 和原文注记，规则生效。
  - 任务取消：只处理本任务列出的条款。新增的删除，编号不复用；修改的恢复原文，保留原编号。
- **编号永不复用：** 新规则接着现有最大编号往下排；删除的规则留空号，不重新编号。
- 改动 `description` 或一级标题时重新生成索引；改动任何标题时检查指向它的链接。
- **吸取教训：** 同一类错误**重复出现**时，提炼成一条规则，写进对应 Spec 或 `AGENTS.md`。只出现一次的不写。

### 3. 验证

- **完成的定义：** 验收清单每一项都有证据，或写明未完成的原因。
- **证据类型：** 测试输出、构建结果、模拟器截图、真机表现或你的确认。各自只证明自己覆盖的范围，比如构建通过不代表行为正确。
- **证据存放：** 放在任务目录的 `evidence/`，任务文件只写路径。
- **怎么测由执行者按任务决定**，Harness 不规定具体步骤。

### 4. 审查

- **何时审查：** 行为改动较大、跨模块改动，或你要求时。小改动和纯文档不强制。
- **审查者：** 在全新的上下文中进行（新会话或子代理），不沿用写代码的对话。
- **输入：** diff、任务的目标与验收清单、相关 Spec。
- **输出：** 只报告影响正确性或违背需求的问题，风格偏好不报。
- **资源开销必查：** 每次审查都依据 [资源规范](../specs/resource-efficiency.md) 给出资源结论；不涉及运行时资源时写明“不适用”及理由。
- **处置：** 由主模型逐条核实，接受或不采纳并写明理由，结论简要记入任务的“决定”。审查意见不自动等于验收结论。

### 5. 上下文组装

| 层 | 内容 | 参考上限 | 何时加载 |
| --- | --- | --- | --- |
| L0 常驻 | `AGENTS.md`：项目事实、常用命令、硬约束、各入口位置；Spec 索引 | `AGENTS.md` ≤ 3KB | 每次会话 |
| L1 任务 | 当前任务的 `task.md`；当前阶段的一个技能 | 各约 3KB | 做该任务时 |
| L2 细节 | 相关 Spec 全文、源码、证据文件 | 按需 | 用到才读 |
| 维护层 | 本契约、Harness 演进记录 | — | 只在维护 Harness 时读 |

- **上限是参考值，把话说清楚优先。** 超出时先删去重复或不必要的内容，不靠压缩措辞凑字数；确需超出时可以稍长。
- **交接给其他模型写代码时：** 交一份自包含的说明（≤ 2KB），写明改哪些文件、目标行为、相关 Spec 规则编号、怎么验证。不要求对方再读 `AGENTS.md` 全文、技能或完整任务记录。
- **交给审查者时：** 按第 4 项的输入提供，不另加材料。
- **判断标准：** 每一份 Harness 文件都要能说出自己属于哪一层；说不出来的，删除或归档。

## 约束方式

规则负责引导，检查放在已有的节点上，最终由你把关：

- **写成简短规则：** 关键要求放在 L0/L1 的显眼位置，不写否定式的边界声明。
- **在已有节点检查：** 最终汇报逐条列出验收状态；归档时核对验收清单；审查时对照 diff 核对清单；你要求提交时顺带核对。
- **Hook：** 只用于机械可判断、零例外的事，并且要在**观察到问题之后**才加；优先只提醒、不拦截。
- **当前没有 Hook**（2026-09-30 移除 Codex Hooks：工具路径覆盖不全、白名单维护成本高）。Hook 只能保证脚本在某时刻运行，不能保证模型判断正确。出现对应问题时再按需添加的候选：
  - 修改 `docs/specs/*.md` 后自动运行 `spec_index.py`；
  - 每轮结束时检查 `git diff --check` 与索引是否过期；
  - 上下文压缩后重新注入当前任务的“下一步”。
- **绝对禁止的操作**（如推送）交给工具的权限或沙箱设置，不用 Hook。

## 不属于 Harness

| 内容 | 放在哪里 |
| --- | --- |
| 模型分工、额度策略 | `AGENTS.md` 中按工具分节的简短说明；具体参数放各工具配置（如 `.claude/agents/`） |
| Git 规则、构建命令、最低系统版本 | `AGENTS.md` 的项目规则部分 |
| 发布记录 | `docs/` 下的项目文档 |
| 讲解风格、注释规范 | 按需加载的项目指南 |
| 领域技能（UI 设计、Logo、调试服务） | `.agents/skills/`，与 Harness 技能并列，但不属于 Harness；`.claude/skills` 是指向它的软链接 |

## 目标文件布局

```
AGENTS.md                      L0
docs/specs/index.md + *.md     L0 索引 / L2 正文
.agents/skills/
  plan-task/  resume-task/  review-task/  archive-task/  update-spec/   L1，每个约 3KB 以内
tasks/TEMPLATE.md              任务记录模板
tasks/active/  tasks/archive/  L1 / 归档
docs/harness/contract.md       维护层（本文）
scripts/harness/spec_index.py  Spec 索引生成（--check 只核对）
```

后续步骤再决定：现有维护层文档如何归档。

## 修改本契约

需经维护者确认。修改时同步检查各层文件是否仍在上限以内。

旧版 Harness（设计、操作说明、记录格式、提案与验证证据等）已于 2026-09-30 删除，可从提交 `2fdf669` 取回。
