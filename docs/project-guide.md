# MinisX 项目指南

按需读取：讲解代码、写注释、做结构分析、调整 UI、处理 Git 与上游、在设备上验证时，只读相关小节。

## 讲解代码

仅在用户要求讲解、分析或学习时使用本节；实现、审查和进度汇报只解释评估工作所需的内容。

**读者背景**：会基础 C++ 语法，不熟悉现代 C++、Swift、SwiftUI 和 iOS 开发。

- 先说明代码实际做了什么，再引入术语；术语首次出现时用一句话解释。
- 只在对比有助于理解时才与 C++ 对比，并优先使用类、对象、指针、值拷贝、回调等基础概念；不用现代 C++ 的高级概念来解释 Swift。
- 不用比喻代替技术解释。Swift / iOS 概念在 C++ 中没有对应物时，直接说明差异。

**复杂代码按以下顺序讲解**（简单问题直接回答）：

1. 这段代码负责什么；
2. 在当前执行流程中，它之前和之后发生什么；
3. 读懂它所需的 Swift / Objective-C / iOS 语法；
4. 对象生命周期、线程、异步任务、状态更新和可能的副作用；
5. 为什么这样实现，以及修改时必须保持哪些条件成立。

讲解时区分三类规则：**语言语法**（Swift / Objective-C 本身）、**平台行为**（SwiftUI、UIKit、沙盒、权限、后台执行等）、**项目逻辑**（MinisX 自己对 Agent、会话、工具、Provider、同步的规定）。

**遇到以下 Swift 特性时，说明它在这段代码中的实际效果**，而不只是报出名称：

- `struct` 与 `class` 的值语义、引用语义；
- 可选值、`if let`、`guard let`、`nil`；
- 协议、扩展、泛型与类型约束；
- 闭包参数、返回值、捕获与 `@escaping`；
- ARC、强引用、`weak`、`unowned`、`deinit`；
- `async`、`await`、`Task`、actor、`@MainActor`；
- `@State`、`@Binding`、`@Published`、`@Environment` 等属性包装器；
- SwiftUI 的 `body`、状态驱动更新和 View 生命周期；
- Swift、Objective-C 与 C 接口之间的桥接。

## 分析范围与代码搜索

- 主要对象是 `src/ios`，优先关注 `Agent`、`Providers`、`NativeOffloads`、`iSH`、`Views`、`Shared` 和各扩展。
- 涉及沙盒或原生依赖时，再看 `deps/ish`、`deps` 下的构建脚本、`src/shared` 和 `docs/specs`。
- 不把 Android 实现混进 iOS 讲解，除非执行路径确实跨平台或用户要求对比。
- 不为 `Vendor`、资源文件、生成文件加注释，除非用户明确要求。
- 结构性问题（定义、调用者、被调用者、执行路径、改动影响）在 CodeGraph 可用且索引较新时优先用它；查询中带上 `src/ios`、完整文件名或明确的 Swift 符号，避免先返回同名的 Android 代码。字面搜索（字符串、日志、已有注释）用 `rg`。CodeGraph 不可用或结果不足时直接读源码。

## 源码注释

- 默认用简洁的中文。
- 写原因、约束、不变量、副作用、线程要求、权限边界、数据约定、边界情况或兼容性处理；不写只复述名称或简单流程的注释。
- 加注释前先读懂整个函数及其调用关系，确保注释与实现一致。
- 过时的注释直接更新或删除，不在旁边再加一条。
- 纯注释任务不重构代码、不改变运行行为。长篇讲解留在对话里，注释只保留维护代码需要的信息。

## UI 调整

- 简单的 UI 调整由用户亲手修改以便学习（见 AGENTS.md）。
- 需要比较效果时，优先为正式组件做 Xcode Canvas 预览，把可调参数集中放置并注明用途；保留用户在预览中的修改，确认后的数值应用到正式实现。流程见 [ios-ui-design：Canvas 协作](../.agents/skills/ios-ui-design/SKILL.md#优先用-canvas-协作调整-ui)。
- 预览无法验证的行为，用模拟器或真机检查。

## Git 与上游

- 个人分析与注释工作在 `ios-annotated` 分支进行。
- `main` 是 MinisX 开发基线：官方 OpenMinis v1.13 加上已接受的 MinisX 定制与 Harness，不是官方 `upstream/main` 的镜像。
- `origin` 指向个人 fork；`upstream` 为官方只读仓库（本地未必已配置）。
- 新的功能或修复分支默认从本地 `main` 创建，需先与用户约定。
- 用户要求提交时，按主题拆成小提交。
- 升级上游时，先查看指定的官方分支或提交，与 MinisX 基线对比，保留已接受的定制与 Harness；不要为了“与上游一致”而把 `main` 替换成或 rebase 到 `upstream/main`。保留已有的注释和历史分支。
- 解决冲突时，核对受影响的注释对新实现是否仍然正确。

## 设备与验证

- 先验证一条有代表性的真实使用路径，并确认观察方法确实能证明所需行为，再扩展到更多设备或状态。部署、启动、截图、测试框架运行成功都只证明各自那一步。
- 执行会改变设备状态的命令前（包括测试运行器隐含的安装部署），核对目标设备标识与已确认的目标一致；不一致就停下。委派时传递同样的目标约束，并核对返回结果中的设备信息。
- 同一种观察方法反复失败、没有新证据时，停止扩展；有具体的新假设时才做有界的下一次检查。
- 产品缺陷要写明真实的触发操作、用户可见的影响和证据，与测试工具问题、未验证的风险分开报告。
