# 原生 iOS 界面设计

交付目标：让 MinisX 的界面清楚、熟悉、响应及时且前后一致，让不熟悉设计的用户能够理解并确认重要选择。面向 SwiftUI／UIKit 的原生界面；“苹果原生感”落实为使用体验，不以玻璃、圆角或动画数量衡量。

沿用仓库 AGENTS.md 和现有 Harness。项目根目录以当前仓库为准，不依赖作者机器的绝对路径；本技能内的参考路径相对当前技能目录。

## 范围与协作

- 新页面、界面改进：提供设计判断和有理由的建议；重要目标与取舍接入项目 plan-task。沿用已有批准，不重新发起确认流程。
- 界面检查：在请求的页面或组件范围内找问题，区分缺陷、待验证疑点和可选改进。用户只要求检查时，不直接修改界面。
- 已批准的 UI 实施：把设计要求带入实现与验证；现有 SwiftUI、UIKit、构建和调试能力按需使用。若环境缺少某项技能，直接核对源码和官方 API，不强制安装依赖。
- 只涉及语言或并发的问题交给相应工程能力，不附带界面重设计。本技能不新增任务目录、审查格式或提交权限；正式审查仍按 review-task 的适用条件执行。

## 先建立依据

先明确用户在这个界面要完成什么，再检查相关视图、复用组件、主题和状态变化。按需观察已有截图、预览或运行界面；只有源码时说明视觉和交互尚未验证，不虚构已看到的效果，也不因缺截图停止可完成的分析。

记录实际技术边界：项目最低系统版本以 AGENTS.md 为准；检查页面是 SwiftUI、UIKit 还是两者桥接，不为统一语言重写已有结构。只选择影响当前任务的状态，例如输入、加载、取消、失败、空内容及完成。

需要引用设计原则、做取舍或检查某个专题时，读取 [Apple 依据与项目应用](references/apple-design.md) 的相关小节，按需打开其中官方资料。分别标明：Apple 官方设计建议、系统/API 限制、本项目的设计判断。新 API 或版本行为另查官方文档；不要把旧演讲的具体参数当作现行平台要求。资料暂不可访问时保留已知依据和待核实项，不把二手转述包装成官方结论。

## 设计判断顺序

顺序用于先解决影响体验的问题，不要求每次填写整张清单。一次小改动只检查有关项。

1. **目标、层级与导航。** 确定主要内容、主要操作及次要信息；用分组、位置、文字和适当强调建立关系。先判断常规导航、菜单、表单或 sheet 是否适合，避免同一功能在不同页面使用不同语义。不为“更简洁”隐藏必要状态或让常用操作更难找到。
2. **复用原生行为。** 优先评估现有组件及系统控件能否满足目标，保留合理的项目样式。需要自定义时说明它解决的具体问题，并检查返回、取消、焦点、键盘、安全区域与辅助功能；不因追求原生感自动替换整个页面。
3. **文字、布局与视觉层级。** 按语义选择文字样式、颜色和图标，检查长中文、较大文字、深浅色及真实内容下的可读性。区分内容与导航/操作层；如采用 Liquid Glass，说明放在哪里及其作用，避免把阅读内容或每层容器都玻璃化。
4. **状态与反馈。** 区分“已按下”“请求进行中”“已成功”与“失败”；即时显示能够确认的状态，异步动作尚未成功时不要给成功反馈。让取消、重试及不可操作状态可理解；声音、触感和颜色不能成为唯一线索。
5. **决定是否需要自定义动效。** 先指出它解释的状态或空间关系，再考虑使用频率与打断需求。已有系统反馈足够时保留原状；自定义动效从当前视觉状态衔接，支持合理的中断和反向操作，不让装饰阻塞输入或遮扰阅读。减少动态效果时仍应能理解状态。
6. **验证一致性与可访问性。** 与相邻页面比较相似操作的表现，按受影响范围选择大字体、VoiceOver、减少动态效果、减少透明度、提高对比度、键盘和窄屏检查。优先解决无法操作、难以理解、读不清及明显延迟，再考虑装饰优化。

## 给用户可判断的方案

用中文解释建议的行为和好处，首次使用必要术语时作简短解释。技术事实由 Agent 查明，不把陌生的 API、曲线或阻尼参数交给用户选。

通常提供：当前问题及证据、建议效果、理由或来源、代价、验证方法。存在重要取舍时比较真正不同的可行方案并给出推荐；没有取舍时直接说明依据，不凑固定数量。若只是作者审美偏好或尚未观察到的风险，明确标注，不能直接作为阻断问题。

默认沿用小步实现、测试、调整。用户需要直观比较且已授权时，可制作少量有实质差异的可交互方案；不强制独立原型阶段，也不把网页原型当作原生 iOS 效果验证。

## 优先用 Canvas 协作调整 UI

项目维护者于 2026-09-27 确认：后续 UI 调整尽可能使用 Xcode Canvas，并提供可由维护者编辑参数、即时查看效果的协作方式。这是项目协作偏好，不是 Apple 平台要求。

- **预览真实组件。** 在已授权的 UI 调整范围内，优先提供 SwiftUI `#Preview`，与正式界面共用组件、样式及布局参数。示例数据仅用于预览，不修改真实会话、凭据或触发真实模型请求；不要维护一套仅外观相似、与生产实现脱节的预览。
- **集中放置可调参数。** 将相关尺寸、字号、留白、元素间距等集中到容易找到的位置，用中文注释解释作用、单位、缩放关系和联动方式。说明内容宽度与包含 padding 的总宽度等容易混淆的口径，以及内容撑开等约束。向维护者给出准确的文件位置、参数入口和刷新方法。
- **提供适量对照。** 根据本次调整选取有代表性的状态，例如一位、两位、三位数字，或长短文字、深浅色。尽量在同一画布中并排或上下展示，保留相邻控件作参照；不为每次小改动强制创建完整状态矩阵。
- **由维护者微调、Agent 收尾。** 维护者可以直接编辑参数并检查效果。Agent 保留这些手动修改；确认后核对正式界面共用已确认参数，更新过时注释和任务记录，再完成与改动相称的验证。已确认的值不再重复征求批准。
- **区分预览与运行验证。** 编译通过不等于 Canvas 已成功渲染。实际观察到的预览和维护者反馈分别记录其来源与范围；键盘、手势、后台、权限、性能等不能靠 Canvas 充分验证的行为，按已授权范围补充模拟器或真机验证。

Canvas 是优先选择，不是阻塞所有 UI 工作的硬性前提。遇到不适合预览的组件或预览环境故障，先做有依据的有限排查，再说明限制并采用与任务相称的替代方式。兼容预览模式属于具体环境的排障选项，不作为所有项目或后续任务默认强制开启的设置。

## 实施与验收

沿用已确认范围，把设计要求转换为可观察结果，例如“请求进行中仍能取消，失败后保留输入并可重试”；先检查系统默认行为，只有实际不足时才调自定义参数。

在实现涉及动效或手势时，查看连续交互或录屏，检查快速重复操作、中断和状态切换；截图只能证明静态外观。按需放慢动画观察过程，并回到正常速度验证。需要真机才能判断的触感、手势和性能，未测就明确列出，不以编译成功代替体验验收。

只报告有证据的结果。设计检查不替代 Harness 的测试、独立审查和主 Agent 判断；不为主观偏好降低或新增已确认的验收要求。
