# 规划任务

交付结果：用户能够理解并确认要做什么、采用什么路线及理由、如何证明完成。读者背景以 AGENTS.md 的 Reader Background 为准；由 Agent 调查事实、解释选项并给出推荐，由用户决定预期行为和重要取舍。

这是项目自定义的轻量规划技能。目标澄清、调研、方案比较和定稿属于同一任务，按已有上下文推进，不强制走完整套步骤。遵循仓库 AGENTS.md；下文项目路径均相对仓库根目录。

## 判断从哪里开始

- 普通解释、能力查询或代码阅读：直接回答，不把问题升级成开发任务。
- 已有计划或任务记录：先读取确认内容；跨会话恢复按项目 resume-task 执行。保留已批准的范围和决定，只讨论新出现的实质问题。
- 新开发或实质性验证任务：先核对相关代码、当前分支和工作区，识别真实使用目标中尚未明确的部分。已有信息足够时，直接给出简短确认稿。即使不计划修改产品代码，设备操作、夹具编写和多场景测试也适用 AGENTS.md 的执行前确认要求。

规划期间可读取代码和文档、进行只读检查、编写计划记录；正式实现前取得用户对计划的确认。讨论方向、查看选项或没有回复均不代表批准。已经明确批准的计划无需再次确认；是否继续实施按用户已有授权判断。

## 澄清目标

从用户希望发生的具体行为开始，确认影响本次实现的范围、约束和验收条件。用实际场景检验歧义，例如“重复事件的一次发生”与“整个重复系列”，不要先让用户选择语言或框架。

问题按依赖顺序提出，每轮聚焦少量能立即决定的问题。每个重要技术问题先说明背景、选项的效果与代价，再给出推荐及理由。术语首次出现时用一句话解释；不能只给 API 名称让用户猜。

代码或官方资料能回答的事实由 Agent 查明。只向用户询问偏好、意图或确实无法获取的信息。不重复询问已有答案，不为覆盖所有可能性穷举无关边界条件。

## 按需调研与比较方案

只调查会影响选择或验收的未知项。先读相关源码，再按需查官方文档等一手资料；根据 AGENTS.md 的 Spec Index 选择适用小节。分别说明已确认事实、基于事实的推荐、需要实施后验证的假设，并保留关键证据位置。

存在实质取舍时，比较真正可行的路线：能否满足目标、用户体验、修改与维护成本、系统限制、验证难度，以及以后改换路线的成本。先比较行为上的差别，再讨论影响这些结果的代码组织。明确推荐及理由；只有一条合理路线时说明依据，不凑方案数量。

调研服务于判断，信息足以选择和安排验证时停止。仍未确认的假设应进入实现计划，优先安排可测试的步骤；若未知项决定路线是否可行，应先说明它如何影响选择，不能把猜测写成已确认能力。不默认启动多 Agent；只有独立工作能带来实际收益时按 Harness 委派。

## 形成确认稿

整理已有讨论，不重新访谈。按任务大小用短段落或列表说明：

- 目标与范围：完成后可观察的行为，以及明确排除的内容。
- 方案与取舍：选择的路线、理由及重要的未采用方向。
- 限制与假设：已知约束、待验证项及关键证据。
- 执行边界：当前对话与工作目录、是否需要新分支/worktree、允许修改的文件/数据、设备标识，以及必要的外部操作。新建用户可见工作对话须由用户明确要求，不能由 Agent 自选。计划使用worktree时，必须在创建或开始使用前直接告知用户，说明本任务为什么需要它、相比当前目录的具体收益，以及位置、分支和基线；不能仅写入记录或事后汇报。该安排纳入用户确认，已有明确确认不重复询问。
- 实现步骤：每一步交付可检查的结果，先验证一条代表性真实使用路径及观察方法，再扩展。
- 投入与停止条件：先做到哪一步再评估；出现何种无效证据、环境限制或范围变化时停止受影响工作并说明。仅记录用户实际给定的时间/token上限，不自行捏造预算。
- 验收标准：具体场景、预期结果、验证方式和当前不可用的检查。

请用户确认或修正确认稿后再正式实现或启动实质性验证；不能先执行再请用户审阅任务。依据 AGENTS.md 记录确认版本、用户原话或可核对出处、授权动作和排除项；有待确认假设时明确保留，不能写成用户决定。足够具体的直接修改指令可作为该有界修改的授权，不要求用户重复确认已经说明的内容。不要把内部函数拆分等常规细节都交给用户决定，也不默认引入独立原型阶段。

小任务可在对话中确认，不强制建文档。复杂或跨会话任务按 docs/harness/record-formats.md 写入 tasks/active/ 的现有任务记录，包含适用的 Spec 阅读清单；计划待确认和已批准应明确区分。已确认内容分别进入“目标与验收”“上下文与决定”“实现计划”，避免另建重复需求体系。按 Harness 更新检查点。

## 交接到实施

确认且获准实施后，先完成一条可测试的功能路径，再测试和调整。目标与方案内的缺陷修复、局部实现选择可自主推进。

新证据要求改变已确认的功能、重要技术路线或验收标准时，说明证据、影响和修订建议，等待用户确认相关变更；期间可继续不受影响的工作。不能通过降低验收标准把失败记为成功。

实施、测试和最终验收沿用现有 Harness；Pi 独立审查按 review-task 的适用条件安排。计划确认不等于实现完成；实现完成不等于验收通过。本技能不授予提交、推送或额外外部操作权限。

任务记录独立于 docs/，默认仅从 tasks/active/ 发现候选。已完成或取消的任务及附件移到 tasks/archive/；规划新任务时不以“了解背景”为由批量读取归档。明确需要某条历史决定时先说明用途，再按具体路径取所需内容。
