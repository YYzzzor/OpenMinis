# 更新 Spec

## 写法

范例：[用量、费用与余额](../../../docs/specs/ios-usage-cost-and-balance.md)。

- 文件开头是一行 YAML `description`，接着是一级标题和一句话说明范围。Spec 索引由 `description` 和一级标题生成。
- 规则按主题分组编号（如 U1、P2），每条一句话：用正面表述，写成可以测试的形式，只写“应该怎样”。实现进度和验证证据属于任务记录，不写进 Spec。
- 两种标记：
  - `[拟议]`：已经确定、但尚未实现并验证的规则；
  - `[待决定]`：还没有结论的问题。
- 按需包含：定义表、不在范围内、待决定、验收场景（注明对应的规则编号）、代码入口。
- 单份建议不超过 7,000 字符；超出时按主题拆分成多份。
- **编号永不复用**：新规则接着现有最大编号往下排；删除的规则留下空号，不重新编号。这样任务、审查和历史记录中的引用始终有效。

## 各时机的操作

- **规划时**
  - 新增规则：分配新编号，标 `[拟议]`。
  - 修改已生效的规则：保留原编号，标 `[拟议]`，并在句末附上修改前的原文 `（原：……）`，作为取消时恢复的依据。
  - 在任务记录中分别列出本任务新增和修改的规则编号。
- **实现中**：按实际情况调整拟议规则；如果调整涉及需求变化，先经用户确认。
- **验证通过后**：去掉 `[拟议]` 标记和 `（原：……）` 注记，规则正式生效。
- **任务取消**：只处理任务记录中列出的条款，不动其他任务的改动。
  - 本任务新增的规则：删除，编号不再复用。
  - 本任务修改的规则：恢复为 `（原：……）` 中的原文，保留原编号。
- **同类错误重复出现**：提炼成一条规则，写进对应的 Spec。只出现过一次的错误不写。
- **改写旧 Spec**：逐条对照代码核对。发现规则与代码不符时，先向用户报告，再决定是改代码还是改规则。不能只换写法而不核对内容。

## 改完后检查

1. 改了 `description` 或一级标题：运行 `python3 -B scripts/harness/spec_index.py` 重新生成索引。
2. 改了任何标题：搜索其他文件中指向旧标题的链接（如 `rg "文件名\.md#"`），逐个更新。
3. 运行 `git diff --check`。
