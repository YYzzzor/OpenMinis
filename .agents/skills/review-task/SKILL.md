# 任务审查

## 准备（主会话）

整理审查输入：
- diff：未提交改动，或 `git diff <基准>..HEAD`；
- 任务的目标与验收清单；
- 相关 Spec 路径；
- 已做的验证和未验证的部分。

## 执行

审查者必须在全新上下文中进行，不沿用写代码的对话：
- Claude Code：使用 `reviewer` 子代理。
- Codex：按 AGENTS.md，开新的 `gpt-6.1-sol` / `high` 会话。
- Pi：暂停使用。用户要求恢复时，按本技能的输入重新接入；旧适配 `scripts/harness/review.py` 可从提交 `2fdf669` 取回参考。

对审查者的要求：
- 只读；只报告影响正确性或违背需求的问题。
- 每条写明严重程度、对应规则或验收项、代码位置、触发条件、依据；确定缺陷与待核实疑点分开。
- **必须检查资源开销**，依据 [资源规范](../../../docs/specs/resource-efficiency.md) 单独给出结论；不涉及运行时资源时写“不适用”及理由。

## 处置（主会话）

- 逐条核实：采纳（修复后针对性复查）、不采纳（写具体理由）、或交给用户判断。
- 结论简要记入任务的“决定”。
- 需要保留原文时，存为 `reviews/<序号> <内容标题>/report.md`。
- 审查结论不等于验收：“无发现”不代表通过，“阻断”也要先核实。
