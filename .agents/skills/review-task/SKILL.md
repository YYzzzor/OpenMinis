# 任务审查

## 准备（主会话）

整理审查输入，写法按 [plan-task 的写法](../plan-task/SKILL.md#写法)。

| 审查 | 何时 | 输入 |
| --- | --- | --- |
| 方案审查 | `task.md` 确认稿写好后、交给用户确认前 | `task.md` 路径；相关 Spec 路径；相关代码入口 |
| 代码审查 | 实现完成后 | diff（未提交改动，或 `git diff <基准>..HEAD`）；任务的目标与验收清单；相关 Spec 路径；已做的验证和未验证的部分 |

## 执行

审查者必须在全新上下文中进行，不沿用写方案或写代码的对话：
- Claude Code：使用 `reviewer` 子代理。
- Codex：按 AGENTS.md，开新的 `gpt-6.1-sol` / `high` 会话。
- Pi：暂停使用。用户要求恢复时，按本技能的输入重新接入；旧适配 `scripts/harness/review.py` 可从提交 `2fdf669` 取回参考。

对审查者的要求：
- 只读。报告按 [plan-task 的写法](../plan-task/SKILL.md#写法) 写。
- **先做对抗性审查**：从第一性原理出发，确认问题本身是否成立，再寻找能推翻核心假设的反例。
- **用奥卡姆剃刀检查**新增的抽象、机制和流程：满足需求的前提下能删去的，列为“可简化”。
- 除“可简化”外，只报告影响正确性或违背需求的问题。
- 每条写明严重程度、对应规则或验收项、位置、触发条件、依据；确定缺陷、待核实疑点、可简化三类分开。
- **必须检查资源开销**，依据 [资源规范](../../../docs/specs/resource-efficiency.md) 单独给出结论；不涉及运行时资源时写“不适用”及理由。

## 处置（主会话）

- 逐条核实：采纳（修复后针对性复查）、不采纳（写具体理由）、或交给用户判断。“可简化”同样逐条处置。
- 方案审查的处置写进 `task.md` 的“决定”，并更新确认稿，再交给用户确认。
- 代码审查的逐条处置记入任务目录的 `verification.md`；影响需求的结论再记入任务的“决定”。
- 需要保留原文时，存为 `reviews/<序号> <内容标题>/report.md`。
- 审查结论不等于验收：“无发现”不代表通过，“阻断”也要先核实。
